Admissions: every contact at a campus hears about an inquiry, one calendar gets booked

Migration 327 split the two jobs that schools.admissions_contact_email had been
doing at once. This is the code that reads it.

Being told an inquiry arrived is a notification — three people can want it and
nothing breaks when all three know. Being the name on a booking link is a
commitment to one person's calendar. The engine now sends staff mail to every
active contact with receives_notifications, while the booking contact alone
signs parent mail, receives its replies, and supplies {{scheduling_link}}.

FALLBACK IS DELIBERATE AND PERMANENT, NOT A MIGRATION SHIM. If the table is
empty for a school, or absent because 327 has not run where this is deployed,
the school's own columns still answer. The error from the query is read rather
than ignored: a missing table, a policy refusal and an empty result all arrive
as an error object nobody is obliged to look at, and falling back silently on a
refusal would mean one person keeps being notified while nobody ever learns why
the other two are not.

The existing drop-guard is extended rather than replaced. A staff template with
no recipient anywhere is still dropped instead of queued as a delivery to the
empty string.

Verified against production before writing: all four campuses have exactly one
contact and one booking contact, so this ships with behaviour unchanged. Adding
a second person is now an insert.

Seven tests cover the resolver, including the two paths that decide whether this
is safe: an unreadable table falls back AND logs, and a school with no contact
anywhere returns nothing to notify.
