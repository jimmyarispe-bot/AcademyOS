Portal: a parent can see their own record, and change it

/portal/profile could neither read a guardian nor write one, and both failures
were silent.

THE READ. It selected `relationship` from guardians. There is no such column —
it is relationship_to_student. PostgREST rejects the whole select on an unknown
column, supabase-js resolves with { data: null, error }, and the page
destructured only data. So guardian was always null, every parent saw their name
rendered as their email address and their phone as an em dash, and nothing was
logged anywhere. The error is read now, and a page that cannot load a family's
record says so instead of rendering a plausible-looking blank.

THE WRITE. The save button called updatePortalPreferencesAction, which writes a
notifications blob and an accessibility blob and never touches guardians. The
form it belongs to is honestly labelled "Communication preferences" and was
never wrong; what was missing was anywhere to change a name, an email or a phone
number — the exact thing the go-live email will ask families to do.

THE POLICY. guardians carried one policy, guardians_staff_all. Staff can see
every guardian at a school they can access; a parent could see nothing,
including themselves. Migration 330 adds SELECT on the row whose user_id is the
signed-in user, and deliberately no UPDATE.

RLS secures rows, not columns. An update policy scoped to "your own row" would
also let a parent working through the API set receives_billing,
financial_responsibility_percent, custody_status or legal_restrictions on it.
Those are the school's facts about a family, not the family's. So writes go
through a server action that locates the row BY SESSION USER — never by an id
from the form, which would be an id a caller could change — and sets four
fields: first name, last name, email, phone.

Saving clears needs_confirmation. The 77 rows built from billing data carry that
flag so a human confirming them can be told from a machine guessing at them, and
this is the human doing it. Those parents are also told plainly that the name
came from billing records and may be wrong, rather than being shown a form that
implies the school already knows who they are.

STILL NOT USABLE, AND THE REASON IS NOT IN THIS COMMIT. Parents have no
accounts: users holds five rows, all staff, and every guardian row has a null
user_id. This policy matches nothing today. Parent account invitation is the
fourth and last link in the chain, and it is the one that remains.
